Found while writing the racing-update test of zb-bf3yyh: when several `zban update` runs change one issue at the same time on btrfs, some runs fail with `not_found` for the issue, even though it exists the whole time. On tmpfs this does not happen.

Cause: `Project::load` lists `.zban/` with `read_dir`. On btrfs, a directory listing taken while another process renames a temporary file over an existing issue file can leave that issue out. A plain listing loop next to a rename loop in one btrfs directory missed the renamed file in 827 of about 175,000 listings (Linux 7.2), and in none on tmpfs. POSIX leaves it unspecified whether a listing returns an entry that is added or removed while the listing runs.

Effects beyond `not_found` from `show` and `update`: `list` can leave the issue out, `delete` can miss a referrer and leave a dangling reference, and closing an issue can miss an open child. This touches `REQ-DAMAGED-DATA` and `REQ-NO-LOST-UPDATES`; see `DES-PROJECT-LAYOUT` and `DES-SHARED-CORE`. It needs a decision on how a read should behave under concurrent replacement (for example, also looking up a named issue by its path, or listing again), recorded in Mara first.

To reproduce, run the racing update helper from zb-bf3yyh with several processes on a btrfs `target/` and only two CPUs (`taskset -c 0,1`), and accept every outcome rather than only `conflict`.

- [ ] Mara records that reads hold a shared lock on `.zban/` while they list it
- [ ] Every listing of `.zban/` holds the shared lock, and a test shows reads no longer miss an issue that another process is replacing

Maintainer decision: read operations hold a shared advisory lock on `.zban/` while they list it, and writes keep the exclusive lock of `ADR-WRITE-LOCK` (zb-0psza8), so a listing never overlaps a rename. Record it in Mara first.
