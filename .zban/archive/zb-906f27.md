Found while writing the racing-update test of zb-bf3yyh: when several `zban update` runs change one issue at the same time on btrfs, some runs fail with `not_found` for the issue, even though it exists the whole time. On tmpfs this does not happen.

Cause: `Project::load` lists `.zban/` with `read_dir`. On btrfs, a directory listing taken while another process renames a temporary file over an existing issue file can leave that issue out. A plain listing loop next to a rename loop in one btrfs directory missed the renamed file in 827 of about 175,000 listings (Linux 7.2), and in none on tmpfs. POSIX leaves it unspecified whether a listing returns an entry that is added or removed while the listing runs.

Effects beyond `not_found` from `show` and `update`: `list` can leave the issue out, `delete` can miss a referrer and leave a dangling reference, and closing an issue can miss an open child. This touches `REQ-DAMAGED-DATA` and `REQ-NO-LOST-UPDATES`; see `DES-PROJECT-LAYOUT` and `DES-SHARED-CORE`. It needs a decision on how a read should behave under concurrent replacement (for example, also looking up a named issue by its path, or listing again), recorded in Mara first.

To reproduce, run the racing update helper from zb-bf3yyh with several processes on a btrfs `target/` and only two CPUs (`taskset -c 0,1`), and accept every outcome rather than only `conflict`.

- [x] Mara records that reads hold a shared lock on `.zban/` while they list it
- [x] Every listing of `.zban/` holds the shared lock, and a test shows reads no longer miss an issue that another process is replacing

Maintainer decision: read operations hold a shared advisory lock on `.zban/` while they list it, and writes keep the exclusive lock of `ADR-WRITE-LOCK` (zb-0psza8), so a listing never overlaps a rename. Record it in Mara first.

## Summary of Changes

- Reproduced first, on btrfs: the new `reads_see_an_issue_that_another_process_replaces` in `tests/simultaneous_changes.rs` runs 8 threads of `zban show` and `zban list` while the test renames a copy of the issue over it under the exclusive lock, as a zban write does. Without the shared lock it failed 30 of 30 runs (`show` gave `not_found`, `list` left the issue out). `parallel_updates_of_one_issue_lose_none` no longer tolerates `not_found`, and failed 10 of 10 runs without the shared lock. The `racing_updates` helper of #26 now requires every run to succeed or fail with `conflict`, and caught `not_found` in 1 of 10 runs without the shared lock.
- Mara: `ADR-WRITE-LOCK` (now "Lock the project directory only around each write and listing") records the maintainer's decision, why the lock covers only the listings, and the rejected alternatives. `DES-SHARED-CORE` describes the shared lock, the "proceed unlocked where locking is unsupported" rule for it, and the rule that a step holding the lock never lists. `VER-ISSUE-FILES` names the new checks. The user docs on simultaneous changes explain it.
- `src/store.rs`: `Project::entries`, the only listing of `.zban/` and `.zban/archive/` (used by `load` and `temporary_files`), runs under `Project::shared`, which takes `File::lock_shared` on a handle of `.zban/`. `locked` and `shared` share `with_lock`, so both proceed unlocked only where `proceeds_unlocked` says locking is unsupported. No caller lists while holding the exclusive lock: the closures in `replace`, `place` and `delete_among` only compare, check the target and rename or remove.
- `replacing_moving_and_deleting_wait_for_the_lock` now holds the lock shared, so each command's own listing goes ahead and the test still fails when any one of the three write sites is unlocked (checked by removing each). The new `reads_wait_for_a_write_but_not_for_another_read` shows that `show` and `list` wait for an exclusive lock but not for a shared one; it fails when the listing is unlocked or takes the lock exclusively (checked).
- Found: a file that another process moves into the other directory after the listing and before the read is still missed (1 `not_found` in 16,000 `show` runs while another process closed and reopened the issue). Mara says so, and zb-45235x tracks it.
- Checks run: `cargo fmt --all -- --check`, `cargo clippy --locked --all-targets -- -D warnings` and `cargo test --locked` on Rust 1.99.1, all passing; `cargo +1.89 test --locked`, all passing; with the fix, `tests/simultaneous_changes.rs` passed 30 of 30 runs on btrfs, 30 of 30 pinned to two CPUs with `taskset -c 0,1`, and 10 of 10 on tmpfs, `update_fails_with_conflict_when_another_run_replaced_the_file` 40 of 40 and `each_error_code_is_produced` 10 of 10; `mara schema validate` and `mara project validate` report valid with complete evaluation; `zban check` reports no problems.
