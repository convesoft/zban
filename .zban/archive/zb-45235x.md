Found while fixing zb-906f27. Since that fix, `Project::load` lists `.zban/` and `.zban/archive/` under the shared lock of `ADR-WRITE-LOCK`, so the listing itself is consistent. It then releases the lock and, for each listed path, checks that it is a file (`is_issue_file`) and reads it. If another zban process closes or reopens that issue in between, `Project::place` renames the file into the other directory: the listed path no longer exists, and the issue is either skipped (`show` and `update` fail with `not_found`, `list` leaves it out) or kept as unreadable (`unreadable`, and `check` reports `unparseable`), although the issue existed throughout. A deletion in the same window is harmless, because the read then behaves as if it came after the deletion.

Reproduced once in 16,000 runs of `zban show ID --json` (8 shell loops of 2,000) while another loop ran `zban update ID --status done` and `--status todo` 2,000 times each, on tmpfs, with the zb-906f27 fix in place.

This needs a decision recorded in Mara first (`ADR-WRITE-LOCK`, `DES-SHARED-CORE`, `VER-ISSUE-FILES`). Options: hold the shared lock until the listed files have been read, but not parsed (simplest; writes then wait for the reads too); or, when a listed file is gone, look for it in the other directory.

- [x] Mara records how a read treats an issue that another process moves after the listing
- [x] A test of the real binary shows `show` and `list` never miss an issue that another process keeps closing and reopening

## Summary of Changes

- Maintainer decision recorded in `ADR-WRITE-LOCK`, `DES-SHARED-CORE` and `VER-ISSUE-FILES`, replacing the known-gap wording from zb-906f27: a read holds the shared lock from listing `.zban/` and `.zban/archive/` until the listed files' bytes have been read, and parses them after releasing it. Writes keep the exclusive lock, and the unlocked fallback where locking is unsupported stays. The user guide on simultaneous changes says the same.
- `Project::load` now lists and reads the files inside one `shared` call; `entries` no longer takes the lock itself, and `temporary_files` wraps its listing in `shared`. No step under the exclusive lock loads or lists (callers of `load` and `temporary_files` re-checked: `check --fix`, `place`, `delete`, `create` and the lifecycle `save` path).
- New `reads_see_an_issue_that_another_process_closes_and_reopens` in `tests/simultaneous_changes.rs`: 8 threads each run `zban show` and `zban list --all` 500 times (8,000 runs) while another thread closes and reopens the issue under the lock as `zban update` does (about 7,900 cycles per run), requiring every read to find the issue with no warning. It shares a helper with the replacement test, which now also uses `list --all` and requires no warnings. No test tolerated `not_found` or `unreadable` for this gap any more.
- Without the fix the new test failed 30 of 30 runs (and 10 of 10 pinned to 2 CPUs), with `list` leaving the issue out, `show` failing with `not_found`, and `show` failing with `unreadable`. With the fix it passed 100 of 100 runs; the whole `simultaneous_changes` binary passed 30 of 30 runs and 10 of 10 pinned to 2 CPUs.
- The original scenario with real processes (8 loops of 2,000 `show` and `list --all` while `zban update` closed and reopened the issue 2,000 times each): `origin/main` missed the issue in 2 of 3 runs, the fix in 0 of 3.
- Checks run: `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (also `cargo +1.89 test --locked`), `mara schema validate`, `mara project validate` (valid, evaluation complete, no diagnostics), `zban check`.
